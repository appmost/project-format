# Appmost Project Format 2.1.1

This is the normative specification for reference release **2.1.1**, using
`documentVersion: 2`. It makes editorial introduction-metadata corrections
to the existing 2.1 feature set; it adds no runtime types, schema fields or
decoder behavior. Renderer availability is separate from reference publication.

The [release manifest](https://www.appmost.ai/format/releases.json),
[current registry](https://www.appmost.ai/format/registry/2.1.1.json),
[schemas](https://www.appmost.ai/format/schemas/2.1.1/page.schema.json) and
[publication errata](https://www.appmost.ai/format/publication-errata.json)
provide the machine-readable identities. Every published versioned artifact,
including a candidate, is immutable.

## Version axes

`documentVersion` is the integer wire-format major. It changes only when
required package structure, an existing field's meaning, or other decoding
semantics become incompatible. A breaking successor to v2 therefore uses
format release 3.0.0 and `documentVersion: 3`.

Specification releases use semantic versions independently of stored project
versions:

- patch releases clarify documentation or make compatible corrections;
- minor releases add compatible optional fields or new semantic row, action,
  and value types; each new type records that release in `introducedIn`;
- major releases make breaking changes and introduce the matching
  `documentVersion`.

### Publication history and introduction metadata

Canonical 2.0 bytes come from public Git commit
[753ad8ae3dcb0369ab3bfb0b09d144d2ade71104](https://github.com/appmost/project-format/tree/753ad8ae3dcb0369ab3bfb0b09d144d2ade71104).
A later website published different bytes under some 2.0 URLs. Those observed,
mislabeled bytes are preserved as historical evidence, not substituted for the
canonical specification. Their first global website publication time is unknown.

The already public 2.1.0 reference remains byte-for-byte unchanged. It incorrectly
labels `donutChart` and the four web appearances as introduced in 2.0.0.
This 2.1.1 reference corrects those five literals to **canonical specification
introduction 2.1.0**. This does not claim that the mislabeled features had never
appeared on the website earlier. The exact historical errors, registry hashes
and canonical baseline are declared in the publication errata; they do not
authorize general backdating, runtime normalization or a compatibility fallback.

The 2.1 feature set includes adaptive layouts, Open page pane destinations,
background overlays, speech transcription, remote row values, donut charts,
chart selection, native navigation/toolbar items and web appearances.
`openAnotherPage` itself remains introduced in 2.0.0; its pane destination
capability is introduced in 2.1.0. Retired `appendToFirebaseDatabase` remains
documented as unsupported and deprecated in 2.1.0, not reintroduced by this patch.

New fields, capabilities and semantic types require a new minor release.
Editorial corrections require a new patch release and URL. A release must keep
prior bytes, schema identities and introduction metadata, validate all adjacent
releases, and publish its manifest, specification, new artifacts and current
links together. Both reference publication and the matching tagged specification
plus production Appmost build are required for a complete product/specification
release; a pending app build never permits altering a public candidate.

## Package

An Appmost project is a directory package ending in `.appmostapp`:

```text
Project.appmostapp/
├── app.json
├── versions/
│   └── <positive-version-number>/
│       ├── version.json
│       ├── localizations.json
│       └── pages/<page-file>.json
└── resources/
```

`resources/` and each `localizations.json` file are optional. All JSON files
MUST be UTF-8 encoded JSON. Core documents MUST contain JSON objects.

Readers MUST resolve paths relative to the package root and MUST reject absolute
paths, parent traversal, path separators in page filenames, symbolic-link
escapes, and any referenced path outside the package.

## Document version

`app.json.documentVersion` and every `version.json.documentVersion` MUST be the
integer `2`. Readers MUST select the document model before decoding other
fields. An unsupported document version MUST fail clearly.

## `app.json`

Required fields:

| Field | Type | Meaning |
| --- | --- | --- |
| `documentVersion` | integer | MUST be `2` |
| `name` | string | Project display name |
| `currentVersion` | positive integer | Active stored version |
| `versionNumbers` | array of unique positive integers | Complete stored-version index |

`currentVersion` MUST occur in `versionNumbers`. `versions/` MUST contain
exactly one numbered directory for every value in `versionNumbers`.

`highestVersion` MAY be present as a positive integer. When present, it MUST NOT
be lower than any stored version number.

## Stored versions

Every `versions/<number>/version.json` requires:

| Field | Type | Meaning |
| --- | --- | --- |
| `documentVersion` | integer | MUST be `2` |
| `version` | positive integer | MUST equal its directory name |
| `startPageId` | non-empty string | ID of the initial page |
| `pageFileNames` | non-empty array of unique strings | Exact page-file index |

Each page filename MUST be a safe basename ending in `.json`. The `pages/`
directory MUST contain exactly the listed files.

`releaseState` MAY be omitted. When present, its only valid value is
`"locked"`. Omission means that the stored version is editable.

Other version properties, including theme, bundle, build, environment, and icon
configuration, are JSON values interpreted by implementations. Portable
extensions should use the namespaced mechanism described below.

## Pages

Every page file requires a non-empty string `id`. Page IDs MUST be unique within
their stored version, and `startPageId` MUST reference one of them.

`rows`, when present, MUST be an array of row objects. Each row requires:

- a non-empty string `id`, unique within the page including nested rows;
- a semantic `type` listed in `registry/2.1.1.json`.

Nested rows use `childProperties.children`, which follows the same row rules.
Rows MAY contain layout and content properties such as `contentPadding`,
`outerMargins`, `labelModels`, `imageViewModels`, and `buttonModels`. Their JSON
shape is preserved unless a property is defined more strictly by this
specification or a future schema revision.

The canonical row names and current renderer support are published in
`registry/2.1.1.json`. The visual catalog at
[appmost.ai/format](https://www.appmost.ai/format/) is explanatory rather than
pixel-normative.

### Chart rows

The semantic row types `barChart`, `lineBarChart`, `areaChart`,
`rangeChart` and `donutChart` read their configuration from the first object in
`chartViewModels`. The public property names, allowed values, preset defaults,
and renderer scope are defined in
[`registry/chart-properties-2.1.1.json`](https://www.appmost.ai/format/registry/chart-properties-2.1.1.json).

Every chart data point MUST contain a string `label` and numeric `value`. A
range data point MAY also contain numeric `minValue` and `maxValue` bounds.
Writers SHOULD provide both bounds for every range point. The order of
`dataPoints` is the rendering order.

`chartStyle` selects one of the `standard`, `compactTrend`, `sparkline`, or
`metricInline` preset defaults. Explicit properties override those defaults.
`usesCustomChartStyle` records that an editor has moved away from the selected
preset; it does not permit a renderer to ignore explicitly stored properties.

Document version 2 uses the correctly spelled `usesGradient` field. The
misspelled `useGradent` spelling is a document version 1 migration alias and
MUST NOT be emitted by a document version 2 writer.

```json
{
  "id": "weekly-demand",
  "type": "areaChart",
  "chartViewModels": [{
    "chartStyle": "standard",
    "usesCustomChartStyle": true,
    "showXAxis": true,
    "showYAxis": true,
    "usesGradient": true,
    "lineWidth": 3,
    "showGridLines": true,
    "showSymbols": false,
    "yAxisPosition": "leading",
    "interpolation": "monotone",
    "dataPoints": [
      { "label": "Mon", "value": 18 },
      { "label": "Tue", "value": 27 },
      { "label": "Wed", "value": 23 }
    ]
  }]
}
```

## Actions, values, and expressions

Rows may declare `appActions` as an array. Each action object requires a
registered semantic `type` and MAY contain a `configuration` object. The
registered action names are listed in `registry/2.1.1.json`.

Page variables use a non-empty `id` and a `valueType` object. The
`valueType.baseType` value MUST be a registered value type. A variable MAY
contain `defaultValue` and additional implementation-defined configuration.

Expression objects use a registered expression type. Typed scalar values MUST
use native JSON booleans and numbers. `longInteger` values use signed decimal
strings so readers based on IEEE-754 numbers do not lose precision.

Unknown required row, action, value, or expression types MUST fail clearly and
MUST NOT be replaced with unrelated behavior.

## Localizations

`localizations.json`, when present, MUST contain a JSON object. Its keys and
values are user content. Readers MUST NOT reinterpret localization keys as core
field or type names.

## Resources

Shared media MAY be stored below `resources/`. References MUST be relative,
remain inside the package, and identify files rather than directories. Readers
SHOULD validate resource size and media type before decoding it.

## Extensions

Any core object MAY contain an `extensions` object. Every extension key MUST be
namespaced using this shape:

```text
owner.example/feature-name
```

The required key pattern is `^[a-z0-9.-]+/[a-zA-Z0-9._-]+$`. Readers and
writers MUST preserve unknown extension values as opaque JSON. Unknown fields
outside `extensions` MAY be accepted for forward reading, but preservation is
not guaranteed.

## Renderer support

Format validity and renderer support are separate. The published row renderer
targets are iOS with SwiftUI and Android with Compose. A renderer MUST report
unsupported required content instead of silently substituting another type.

## Appmost Design support

Appmost Design reads document version 2 packages and uses the iOS SwiftUI
renderer for its preview. Its preview supports every row whose
`support.appmostDesignPreview` registry flag is `true`.

Preview support does not imply that every property of the row has a dedicated
editor control.

Appmost Design intentionally exposes fewer runtime features than the full app
targets. An action is available in its editor and interactive preview only when
the action's `support.appmostDesign` flag is `true`. Value types distinguish
between `support.appmostDesignReadable` and
`support.appmostDesignSelectable`.

These flags describe the product surface, not format validity. A registered
type remains valid even when Appmost Design does not offer an editor for it.

## Validation errors

The reference validator reports stable machine-readable codes where possible:

- `broken_reference`
- `duplicate_id`
- `invalid_json`
- `invalid_package`
- `invalid_typed_value`
- `missing_document_version`
- `unknown_action_type`
- `unknown_row_type`
- `unknown_value_type`
- `unsafe_path`
- `unsupported_document_version`

Implementations MAY provide additional diagnostics but SHOULD retain the
closest stable code.

## Security

Packages are untrusted input. Implementations MUST enforce package boundaries
and MUST NOT execute project strings, expressions, or resource content as host
code. Implementations SHOULD apply limits to file count, nesting depth,
individual file size, total expanded size, and decoded media dimensions.

## Web appearance

`globalTheme.webAppearance` selects the visual treatment of Appmost's adaptive
web navigation without changing page-graph semantics. The supported values are:

- `standard`: calm solid navigation surfaces and restrained separators;
- `glass`: inset translucent navigation surfaces with blur and elevation;
- `brand`: solid navigation surfaces driven by the app accent colors;
- `material`: tonal Material navigation surfaces with active indicators and
  adaptive rails on wider viewports.

The field defaults to `standard`. Every appearance uses the same responsive
placement rules: compact viewports show top-level destinations in a bottom tab
bar, while wide non-modal viewports show them in a sidebar or navigation rail.
Page-local back, title, and action controls remain in the navigation bar.
Root tab destinations do not acquire back or dismiss controls from the shell;
those controls are shown only by page hierarchy or explicit app actions.
Renderers MUST NOT use the appearance to infer app type, authentication, or
page visibility.

## Dynamic navigation-item icons

Navigation and toolbar button items use `imageNameVarExpVal` for their icon.
The value is a normal variable-expression value of icon-name type, so it may
be a constant icon, a variable reference, or a resolved expression. This lets
an item change between state-specific Material icon names, for example
`heart-outline` and `heart`, without replacing the page or adding a second
button.

V2 writers MUST emit `imageNameVarExpVal`. Readers MAY accept the legacy
constant `image` string when opening older projects, but MUST normalize it to
an icon-name variable-expression value when the project is saved as v2.
Resource discovery MUST include every statically discoverable result from the
expression so all possible icons are packaged for native and web renderers.

## Adaptive pages and pane destinations

An `adaptive` page composes existing `normal` pages through `layout`.
It MUST NOT also contain rows or tabs. Layout describes content relationships;
screen dimensions, density, orientation, safe areas and physical folds belong
to the rendering environment, not device-specific document layout objects.

```json
{
  "id": "workspace",
  "type": "adaptive",
  "layout": {
    "kind": "navigationSplit",
    "panes": {
      "primary": {"pageId": "list"},
      "secondary": {"pageId": "detail", "emptyPageId": "empty"}
    },
    "compact": {"behavior": "stack", "initialPane": "primary"},
    "expanded": {"sizing": "automatic"}
  }
}
```

`kind` is `navigationSplit` for list/detail or `split` for content/support.
Both panes MUST be present and reference distinct existing normal pages.
Only secondary may declare `emptyPageId`, which MUST also reference a normal
page. Nested adaptive pages, unknown layout keys, undefined references and
`layout` on another page type are invalid. An initial pane page that requires
mandatory navigation parameters needs a normal empty page instead.

Omitted `compact` defaults to `{"behavior":"stack","initialPane":"primary"}`.
If supplied, both supported fields are required; `initialPane` is
`primary` or `secondary`. Omitted `expanded` defaults to
`{"sizing":"automatic"}`; if supplied, `sizing` MUST be `automatic`.

Pane replacement is an optional destination of the existing `openAnotherPage`
action, not a separate action type:

```json
{
  "type": "openAnotherPage",
  "targetId": "detail",
  "configuration": {
    "containerId": "workspace",
    "paneId": "secondary",
    "operation": "replace"
  }
}
```

Omit all three destination fields to retain ordinary navigation. If any is
present, all MUST be valid: `containerId` references an adaptive page,
`paneId` is `primary` or `secondary` and `operation` is
`replace`. The target MUST be a normal page. Pane destinations on another
action, indirect navigation, sheet presentation or awaiting a page result
cannot be combined with pane replacement.

The renderer resolves the visible ancestor container instance. An action
outside that instance fails; containers do not share pane-local page state.
Mandatory target parameters must resolve before replacement. Replacing a pane
does not rewrite its authored page reference or accumulate selection history.
A compact presentation shows the selected pane; expanded presentation uses
the actual available content regions. Document validity does not guarantee a
particular device's fold integration or renderer-specific width thresholds.

## Background contrast overlays

`appearance.backgroundOverlays` is an optional ordered array of contrast
overlays. It adds no content rows. Each overlay uses:

- optional nonempty `id`, unique among overlays;
- `direction`: `topToBottom` (default), `bottomToTop`,
  `leftToRight` or `rightToLeft`;
- fractional `start` and `end` in [0,1], defaulting to 0 and 1,
  with `start < end`;
- finite `offset` and positive finite `length`, defaulting to -80 and 180;
- optional `anchorRowId` referencing an existing scrolling, nonsticky row;
  anchoring is supported only for `topToBottom`;
- at least two `stops` in nondecreasing `location` order.

Each stop has fractional `location` and `opacity` in [0,1], a six-digit
RGB hex `color`, optional six-digit `darkColor`, and optional nonempty
`id` unique within that overlay's stops. Invalid positions, colors,
duplicate IDs or missing anchor rows fail validation. Overlays do not alter
the page graph, safe areas or user content.

## Chart selection and native navigation items

`donutChart` and the chart reference's `highlightedDataPointIndex`
support the existing 2.1 selection representation. A selected donut segment
may be exploded according to the chart reference; no new chart property is
introduced by 2.1.1. Data-point order remains the rendering order.

Pages may declare `leftNavBarButtons`, `rightNavBarButtons` and
`bottomToolbarItems` arrays using the schema's `barButtonItem` definition.
Their icons use the variable-expression icon field described above.
Platform placement and native material appearance are renderer concerns;
presence in the format does not imply that every product exposes the same
authoring or publishing feature.

## Speech transcription and remote row values

`transcribeSpeech` is an action type introduced in canonical specification
2.1.0. `remoteRows` is a value type introduced in 2.1.0. Their current
platform support and Appmost Design authoring/readability flags are explicit
in the semantic registry; readers MUST NOT infer support from the decoder major
or silently substitute another action or value type. Product credentials,
permissions and backend availability remain independent runtime requirements.
