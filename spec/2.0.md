# Appmost Project Format 2.0

This document defines document version 2 of Appmost Project Format. The key
words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY describe requirement levels.

## Package

An Appmost project is a directory package ending in `.appmostapp`:

```text
Project.appmostapp/
├── app.json
├── versions/
│   └── <positive-version-number>/
│       ├── version.json
│       ├── localizations.json
│       └── pages/<page-file>.json
└── resources/
```

`resources/` and each `localizations.json` file are optional. All JSON files
MUST be UTF-8 encoded JSON. Core documents MUST contain JSON objects.

Readers MUST resolve paths relative to the package root and MUST reject absolute
paths, parent traversal, path separators in page filenames, symbolic-link
escapes, and any referenced path outside the package.

## Document version

`app.json.documentVersion` and every `version.json.documentVersion` MUST be the
integer `2`. Readers MUST select the document model before decoding other
fields. An unsupported document version MUST fail clearly.

## `app.json`

Required fields:

| Field | Type | Meaning |
| --- | --- | --- |
| `documentVersion` | integer | MUST be `2` |
| `name` | string | Project display name |
| `currentVersion` | positive integer | Active stored version |
| `versionNumbers` | array of unique positive integers | Complete stored-version index |

`currentVersion` MUST occur in `versionNumbers`. `versions/` MUST contain
exactly one numbered directory for every value in `versionNumbers`.

`highestVersion` MAY be present as a positive integer. When present, it MUST NOT
be lower than any stored version number.

## Stored versions

Every `versions/<number>/version.json` requires:

| Field | Type | Meaning |
| --- | --- | --- |
| `documentVersion` | integer | MUST be `2` |
| `version` | positive integer | MUST equal its directory name |
| `startPageId` | non-empty string | ID of the initial page |
| `pageFileNames` | non-empty array of unique strings | Exact page-file index |

Each page filename MUST be a safe basename ending in `.json`. The `pages/`
directory MUST contain exactly the listed files.

`releaseState` MAY be omitted. When present, its only valid value is
`"locked"`. Omission means that the stored version is editable.

Other version properties, including theme, bundle, build, environment, and icon
configuration, are JSON values interpreted by implementations. Portable
extensions should use the namespaced mechanism described below.

## Pages

Every page file requires a non-empty string `id`. Page IDs MUST be unique within
their stored version, and `startPageId` MUST reference one of them.

`rows`, when present, MUST be an array of row objects. Each row requires:

- a non-empty string `id`, unique within the page including nested rows;
- a semantic `type` listed in `registry/2.0.json`.

Nested rows use `childProperties.children`, which follows the same row rules.
Rows MAY contain layout and content properties such as `contentPadding`,
`outerMargins`, `labelModels`, `imageViewModels`, and `buttonModels`. Their JSON
shape is preserved unless a property is defined more strictly by this
specification or a future schema revision.

The canonical row names and current renderer support are published in
`registry/2.0.json`. The visual catalog at
[appmost.ai/format](https://www.appmost.ai/format/) is explanatory rather than
pixel-normative.

## Actions, values, and expressions

Rows may declare `appActions` as an array. Each action object requires a
registered semantic `type` and MAY contain a `configuration` object. The
registered action names are listed in `registry/2.0.json`.

Page variables use a non-empty `id` and a `valueType` object. The
`valueType.baseType` value MUST be a registered value type. A variable MAY
contain `defaultValue` and additional implementation-defined configuration.

Expression objects use a registered expression type. Typed scalar values MUST
use native JSON booleans and numbers. `longInteger` values use signed decimal
strings so readers based on IEEE-754 numbers do not lose precision.

Unknown required row, action, value, or expression types MUST fail clearly and
MUST NOT be replaced with unrelated behavior.

## Localizations

`localizations.json`, when present, MUST contain a JSON object. Its keys and
values are user content. Readers MUST NOT reinterpret localization keys as core
field or type names.

## Resources

Shared media MAY be stored below `resources/`. References MUST be relative,
remain inside the package, and identify files rather than directories. Readers
SHOULD validate resource size and media type before decoding it.

## Extensions

Any core object MAY contain an `extensions` object. Every extension key MUST be
namespaced using this shape:

```text
owner.example/feature-name
```

The required key pattern is `^[a-z0-9.-]+/[a-zA-Z0-9._-]+$`. Readers and
writers MUST preserve unknown extension values as opaque JSON. Unknown fields
outside `extensions` MAY be accepted for forward reading, but preservation is
not guaranteed.

## Renderer support

Format validity and renderer support are separate. The published row renderer
targets are iOS with SwiftUI and Android with Compose. A renderer MUST report
unsupported required content instead of silently substituting another type.

## Appmost Design support

Appmost Design reads document version 2 packages and uses the iOS SwiftUI
renderer for its preview. Its preview supports every row whose
`support.appmostDesignPreview` registry flag is `true`.

Preview support does not imply that every property of the row has a dedicated
editor control.

Appmost Design intentionally exposes fewer runtime features than the full app
targets. An action is available in its editor and interactive preview only when
the action's `support.appmostDesign` flag is `true`. Value types distinguish
between `support.appmostDesignReadable` and
`support.appmostDesignSelectable`.

These flags describe the product surface, not format validity. A registered
type remains valid even when Appmost Design does not offer an editor for it.

## Validation errors

The reference validator reports stable machine-readable codes where possible:

- `broken_reference`
- `duplicate_id`
- `invalid_json`
- `invalid_package`
- `invalid_typed_value`
- `missing_document_version`
- `unknown_action_type`
- `unknown_row_type`
- `unknown_value_type`
- `unsafe_path`
- `unsupported_document_version`

Implementations MAY provide additional diagnostics but SHOULD retain the
closest stable code.

## Security

Packages are untrusted input. Implementations MUST enforce package boundaries
and MUST NOT execute project strings, expressions, or resource content as host
code. Implementations SHOULD apply limits to file count, nesting depth,
individual file size, total expanded size, and decoded media dimensions.
